= Contributing to Spring Data DynamoDB

Bug reports, documentation improvements and code contributions are welcome.
For a new API or a substantial change, open an issue to discuss the use case and
design before submitting a pull request. Please follow the
link:CODE_OF_CONDUCT.adoc[code of conduct] and report vulnerabilities through the
link:SECURITY.adoc[security policy].

== Development setup

Install Java 17 or later, fork and clone the repository, then run:

[source,shell]
----
./mvnw verify
----

On Windows, use `mvnw.cmd verify`. The Maven Wrapper downloads Maven and verifies
its distribution checksum. The first build requires network access. You can also
use a local Maven installation at version 3.9 or later.

The compiler targets Java 17. CI builds with Java 17 against both the baseline
and compatibility Spring Boot versions declared in the link:pom.xml[parent POM].
Run the compatibility build locally with:

[source,shell]
----
./mvnw -Dspring-boot.version=4.1.1 verify
----

Use the current `spring-boot.compatibility.version` from the parent POM if it
differs from this example.

== Project structure

* `spring-data-dynamodb`: Spring Data integration independent of Spring Boot.
* `spring-data-dynamodb-spring-boot`: Spring Boot configuration and integration.
* `spring-data-dynamodb-spring-boot-starter`: dependency-only starter, with no Java sources.
* `spring-data-dynamodb-distribution`: documentation and release distribution.

Keep Boot dependencies and types in the Boot integration module. Do not shade
Spring Data or AWS SDK packages. The
link:src/main/antora/modules/ROOT/pages/architecture.adoc[architecture guide]
describes the package boundaries and module names.

== Code style

Follow `.editorconfig`: UTF-8, four spaces for Java and XML, and two spaces for YAML.
Keep dependency and plugin versions in the parent POM. Child modules inherit the
project version; dependencies between modules use `${project.version}`.

Use `DynamoDB` in prose, `dynamodb` in artifact IDs and packages, and `DynamoDb`
in Java class names. Application configuration belongs under `spring.data.dynamodb`.
Public documentation lives in `src/main/antora`.

== Tests

Include tests that demonstrate the behavior of your change and cover relevant
failure cases. Keep unit tests independent of local AWS profiles, credentials and
network access. Test Boot configuration with `ApplicationContextRunner`, including
user-provided beans, disabled features, missing dependencies and invalid settings.
For resources such as clients, verify who owns them and when they are closed.

Integration tests should use DynamoDB Local with test-owned tables and credentials.
They must not access real AWS accounts. Keep unit and context tests runnable with
`./mvnw test` without a container runtime; run integration tests through Failsafe
with `./mvnw verify`. An unavailable container runtime must produce a clear failure
when integration tests are required.

The project currently has no Java implementation or tests. As functionality is
added, contributions must include its tests and build configuration. The coverage
policy is at least 90% line and 85% branch coverage for each implemented core or
Boot module, measured with JaCoCo. These checks will become active with the first
implementation. Any exclusions need a specific justification in the pull request;
configuration and error-handling code are part of the coverage requirement.

Use assertions about results, failures and side effects to establish correctness.
Coverage percentages help identify gaps but do not replace those assertions.

== Pull requests

* Keep the change focused and describe the problem it solves.
* Add or update tests and user-facing documentation where behavior changes.
* Add a changelog entry for changes that affect users or contributors.
* Run the baseline and compatibility builds before requesting review.
* Include the commands and results in the pull request description.

Do not commit credentials, local Maven settings, signing keys, deployment tokens
or build output. Contributions are licensed under the project's Apache License 2.0.

== Dependency updates

Dependabot opens weekly Maven and GitHub Actions pull requests. Keep the baseline
Boot BOM on the lowest supported minor line. Changes to that baseline require a
compatibility review. Update `spring-boot.compatibility.version` in the parent POM
when adding a supported Boot minor; CI reads this property directly.
